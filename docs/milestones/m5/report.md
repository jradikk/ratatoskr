# M5 — production node-agent driver implementation report

Status: **code, local component gates and restricted-Pod startup smoke pass; final packet-level e2e is deferred**. This report does not assert that an agent-managed workload egressed through a healthy real gateway or that established VPN connections survived an agent restart.

## Built

- Node DaemonSet uses the local CRI sandbox identity (namespace, name, UID, ready state and PodIP), corroborates the reported netns with the sandbox PID/cgroup/netns inode, rejects both its own and the node host namespace, and only then enters the selected Pod netns on a pinned OS thread. It restores the original namespace even on programming errors.
- `driver: agent` injects a capability-free restricted-compatible wait-init. It cannot read an ordinary API token; its private emptyDir shadow mount leaves the workload's existing ServiceAccount/fsGroup choices intact. It polls the `rtk-ready` dummy link, which the node agent brings UP **last**, after installing routes, nft rules and fail-close fallback.
- The agent watches assigned Pods and gateway endpoints and periodically resyncs. It hashes authorized configs, adopts an already-UP matching marker after restart without replacing existing tunnel state, recomputes MTU from each workload's own eth0, and updates fixed gateway PodIP routes in place. For encrypted mode, it obtains a Pod UID-bound short-lived TokenRequest in memory, restores the host netns, verifies the gateway TLS identity and registers the peer before installing a usable WG tunnel route. No private key or token is written to a Kubernetes object or the repository.
- Controller leaves agent-mode datapath-ready annotations to the agent, rather than incorrectly interpreting a still-running wait-init as a failed M2 init. Chart now defaults to the agent driver for production and renders scoped RBAC, hostPID/hostNetwork node agent and a read-only CRI/netns mount only in the operator namespace. `hack/dev-values.yaml` retains init mode; `hack/dev-agent-values.yaml` targets the existing flannel k3d cluster.

## Validation on October 29, 2026

- Repository-wide `make test` (race/coverage), `make test-privileged`, `make lint`, `make vet`, `make build`, strict Helm lint and parsed agent/init chart static checks: **passed after the final RBAC/cache fix**; no e2e suite was executed.
- `make dev-images` built and imported six images; a chart upgrade with `hack/dev-agent-values.yaml` succeeded on the existing flannel k3d cluster. Three node agent Pods became **3/3 Ready**; the controller and webhook Deployments were **1/1 Available**.
- A complete test manifest created a `restricted` PSA namespace and an EgressGateway referring to a deliberately nonexistent upstream Secret. After correcting the webhook's uncached Namespace/Pod/Service reads and Pod-list RBAC, rebuilding/importing its image and **rolling the webhook Deployment** to that new image, a labeled workload Pod passed server-side admission dry-run with **no added capabilities**, `RuntimeDefault`, and `-wait-agent`. A real Pod started the unprivileged wait-init but remained **Pending**, its workload container stayed `PodInitializing`, and `datapath-ready` stayed `pending` while gateway condition `SecretUnavailable` was false-ready. No workload packet or real VPN configuration was used. Component Pod, gateway and namespace were deleted after this check.
- Agent ServiceAccount authorization for Pod-bound TokenRequest was checked by RBAC (`kubectl auth can-i ... --subresource=token`), without creating or printing any token.
- A second server-side dry-run with normal workload ServiceAccount automount enabled showed the application retained its ordinary projected API-token volume while the capability-free agent wait-init mounted **only** its emptyDir shadow at the default token path; the wait-init did not mount the actual token. No token contents were queried or printed.
- Cleanup removed the temporary Gateway and restricted namespace; the node DaemonSet rolled out again at **3/3 Ready**.

## Deferred and open

- Full M5 acceptance (working tunnel from a PSA-restricted client, established connection continuity after agent restart, endpoint IP changes, agent/node restart and WG registration/return path) is **not yet packet-tested**. No `make e2e` or `make e2e-live` run or success is claimed; the user requires e2e at the final project gate.
- The component Pod intentionally had no healthy endpoint. The agent reported MTU unavailable and did not mark ready, as designed; CRI setns/marker-up through a healthy real gateway under container RuntimeDefault still needs that final validation.
- The node agent's hostPID/CRI socket, SYS_ADMIN+NET_ADMIN and cluster-wide Pod/TokenRequest permissions are node-root-equivalent. Restricted **workloads** receive none of these permissions, but operators must secure the agent node placement and API credentials. Runtime-specific CRI paths outside the validated k3d/containerd shape fail clearly rather than guessing.
- M6 eBPF, M7 HA/observability, M8 compatibility and M9 release are pending. Live OpenVPN inputs must not be copied or logged; unset `RATATOSKR_E2E_OVPN` at the final gate is a **skip**, not a pass.
